# Préparation de la recette visuelle — vérification encore bloquée

Le navigateur distant n’a pas pu joindre le serveur Vite local (`ERR_CONNECTION_REFUSED`). Une page locale de recette autonome a ensuite été générée à partir du composant réel et du CSS compilé, mais le navigateur interdit le protocole `file:`. Aucun contournement de cette restriction n’a été tenté. Aucune capture visuelle ni validation mobile ou Safari n’a donc été obtenue.

Le script `scripts/recette/habitudes-visuel.mjs` prépare cette page pour un navigateur local autorisé. Il emploie les modèles proposés et le composant réel ; le transport Supabase est remplacé à la compilation par une réponse fictive, sans authentification ni écriture. La page est explicitement étiquetée « recette visuelle ». Deux cadres de 390 et 320 pixels permettent une première comparaison de mise en page. Ce sont des cadres de largeur fixe, pas une émulation iPhone ni une preuve de compatibilité Safari. Les fontes et ressources de la compilation principale ne sont pas intégrées à cette page ; vérifier aussi la version complète avec ses ressources avant de conclure sur la typographie.

Prérequis : exécuter une compilation Vite récente du projet, puis `node scripts/recette/habitudes-visuel.mjs /dossier/temporaire`. Servir ou ouvrir le dossier dans un environnement local autorisé. Le générateur requiert esbuild, déjà présent comme dépendance de Vite. Les fichiers produits sont des intermédiaires de recette, pas une publication ni une inscription réelle.

Corrections de structure réalisées par inspection du code : les libellés de créneau sont des blocs pour garder leurs bordures et leurs champs dans la carte ; champs horaires et boutons limités à la largeur disponible ; retours à la ligne des libellés longs ; zone de confirmation avec espacement, case de 20 pixels et hauteur minimale de 44 pixels ; focus clavier visible. Ces propriétés CSS ne démontrent pas à elles seules l’absence de débordement dans un navigateur.

Après ces ajustements, 29 tests React ont réussi (inscription, catalogue et horaires), ainsi que la vérification TypeScript et la compilation Vite avec le module activé. Ils couvrent notamment la confirmation explicite, le verrouillage pendant la demande, la réponse incertaine, les changements de compte et les états du catalogue ; ils ne remplacent pas un parcours au clavier dans un navigateur. Auth et RPC réelles restent couvertes par la recette HTTP précédente. Aucun changement en base ou sur le site public n’est effectué pendant cette étape.

À vérifier visuellement dans un environnement accessible : carte et bouton à 320/390 pixels, ouverture des détails longs, saisie native des heures, parcours au clavier, confirmation, message d’erreur puis reprise, date de fin, zoom et version anglaise. La recette complète avec une session de navigateur authentifiée reste aussi à faire.
